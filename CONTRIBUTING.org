#+TITLE: Contributing to Harness Investigations

* Scope

This repository contains source-backed harness documentation, reproducible
experiments, and the archive/changelog pipeline. Keep changes focused on one
of those purposes. Preserve unrelated local work and generated archives.

* Documentation and experiments

Use org-mode for documentation, descriptive lowercase filenames, and a
=#+TITLE:= line. Put user-facing behavior under =features/=, implementation
explanations under =internals/=, and reusable procedures under =docs/=.
Update the relevant index when adding a document.

For claims about a harness, record the inspected version, source path, and
supporting lines or runtime evidence. Distinguish released behavior from
unreleased source, experiments, and inference. Recheck version-sensitive
claims before presenting them as current.

Experiments belong in a self-contained directory under =experiments/=. Include:

- The question or hypothesis and the configuration used.
- Reproduction commands, inputs, and session or artifact references.
- Observations, negative results, and limitations.
- Quantitative results with the number of trials when applicable.

Do not commit credentials, personal session transcripts, or raw source archives.
Use [[./docs/experiment-template.org][the experiment template]] where it fits, and
[[./docs/evaluation-methods.org][evaluation methods]] for measurement guidance.

* Pipeline changes

Read [[./docs/changelog-operations.org][Changelog Operations]] before modifying scheduling, source extraction,
authentication, generation, or publication. The service wrapper and scheduler
configuration live in =~/config=, while the processing code lives here.
Changes to either side should be explained together when they affect behavior.

Install Node dependencies with =npm ci=. Validate Python changes with
=python3 -m unittest discover -s tests -v= and
=python3 -m py_compile tools/*.py=. Use =git diff --check= for whitespace.
Add focused regressions for bugs that could skip work, publish bad output,
duplicate messages, or commit unrelated files. Mock external services in tests;
use an explicitly scoped live run to verify authentication or delivery.

Report exactly what the checks prove. Passing offline tests is not evidence
that a scheduled job has run or a webhook has received a message.

* Review and Git workflow

The current integration branch is =main=. Use a focused branch or local change
for review; the repository does not use a separate =develop= integration flow.
A review should explain the problem, resulting behavior, validation, and any
remaining limitations. Keep documentation about the current implementation.

Source changes and service restoration do not imply permission to commit or
push those changes. Automatic archive commits are a separate, configured
service behavior. Keep generated content and code changes distinguishable.

When committing, follow the shared agent instructions: write the complete
message to =commit-msg=, commit with =git commit -F commit-msg=, remove the
message after success, and use an =Assisted-by:= trailer naming the assistant
and precise model variant.
